# CLAUDE.md

This file provides guidance to AI coding assistants (Claude Code, HaiCode itself, or similar tools) when working with code in this repository.

## Build

```bash
# All commands run from the repo root.
# Configure (only needed once)
cmake -B build -S .

# Build everything
make -C build -j4

# Run the full test suite (registered with CTest)
ctest --test-dir build --output-on-failure

# Build individual targets
make -C build haicode-gui
make -C build test_db
make -C build test_diff
make -C build test_git_find
make -C build test_process
make -C build test_file_tools
make -C build test_config_permission
make -C build test_config_write
```

Build type defaults to `RelWithDebInfo` when none is given; all targets compile with `-Wall -Wextra` (keep new code warning-free). Missing `sqlite3`/`curl`/`libcrypto` libraries abort configure with the matching `pkgman install` hint instead of failing at link time.

**Hybrid (x86_gcc2) systems:** HaiCode requires a C++20 compiler, so on a hybrid image it must be built under the secondary-arch toolchain (GCC 13), not the default gcc2. The root `CMakeLists.txt` enforces this: a `cxx_std_20` feature check aborts configure with an actionable message if the compiler can't do C++20, and a secondary-arch detection block reads the compiler's target macros (`__x86_64__` → `x86_64`, `__i386__` → `x86`) to prepend `/lib/<arch>` to the `find_library` HINTS (`HAIKU_DEVELOP_LIB_DIRS` / `HAIKU_LIB_DIRS`). On a pure single-arch system the `<arch>` subdirs don't exist and `find_library` falls through to the flat path. When adding a new `find_library`, use `HINTS ${HAIKU_DEVELOP_LIB_DIRS} ${HAIKU_LIB_DIRS}` rather than hardcoding the flat paths. Headers are single-location on hybrid builds, so `include_directories` is unaffected.

**Single instance (enforced).** The app signature `application/x-vnd.haicode` carries `B_SINGLE_LAUNCH` (compiled from `gui/haicode.rdef` and attached via `rc`/`xres` in the GUI build): a second launch does not start a new process — the running instance is activated and any project-directory argument is forwarded to its window (`HaiCodeApp::ArgvReceived`/`RefsReceived` → MainWindow's `B_REFS_RECEIVED` handler → `MSG_DIR_PROPOSED`). Agents must still never spawn a second copy for testing; verify runtime behavior in the already-running instance.

**Disruptive changes confirm first** (Task 16): `MSG_SETTINGS_SAVED`, `MSG_PROVIDERS_UPDATED`, and directory switches all route through `HaiCodeApp::_ConfirmDisruptiveChange()` before mutating anything. The check lists **every** running session (background ones included, titled, capped at six plus a "…and N more" line) and offers Cancel (default, Escape — leaves app, window, DB, and config files completely unchanged) vs. "Interrupt and Apply". Directory selection is app-owned end to end: MainWindow's `B_REFS_RECEIVED` handler only *proposes* (`MSG_DIR_PROPOSED`); the app confirms, then sends `MSG_DIR_APPLY` for the window-side half (label, skills, session DB row) which replies `MSG_DIR_CHANGED` for the app-side half (config reload, trust prompt, engine recreate). An accepted replacement interrupts **all** running sessions deliberately (not just the active one) in `_RecreateEngine()`.

**`/retry` command:** typing `/retry` (exact match) in the GUI input deletes the last turn's assistant output and re-runs the agentic loop on the stored prompt. Intercepted in `MainWindow::_SubmitPrompt` before submission (never stored, never matched against skills); the engine side is `SessionEngine::retry_last_turn` — keeps the `user_prompted` row (so attachments/skill blocks/mode notices re-apply automatically), deletes only `seq > last_prompt_seq`, refuses while running. `SessionStore::delete_messages_after` also drops (in the same transaction) every compaction checkpoint covering a deleted row or created at/after the kept prompt row — an auto-compaction inside the retried turn summarized discarded work, and its boundary would otherwise hide the re-run's rows, whose seqs are reused.

**Tool-exchange integrity:** every persisted assistant tool batch receives a result for every call, including `success=false` / `not run: <reason>` for calls skipped after denial, plan proposal, or interruption. `ContextBuilder::assemble_messages` groups all responses into one following user message and sets `is_error` on failures. Its provider-only repair associates late legacy responses with their originating calls, removes duplicate/orphan responses, and synthesizes missing results; stored history stays unchanged.

**Prompt scheduling:** `submit_prompt` captures attachments and slash-skill metadata immediately, then claims an idle session or queues the prepared row under `mu_`. Only the worker persists `user_prompted` and publishes `Prompted`; each queued prompt runs as a distinct FIFO turn after the current exchange is complete. The drain re-arms interruption/permission state and atomically checks the queue when clearing the running flag. Shutdown discards queued work. `PromptQueued` updates GUI feedback without resetting current counters/todos; `Prompted` resets per-turn counters when the turn starts. `TurnEnded` signals the foreground completion boundary; `StepEnded` reports usage, not idle state. Completed todos clear only when a new prompt actually starts.

**Image correctness:** user images and screenshot results stay raw only for the current and immediately preceding user turn. Older images become placeholders or persisted descriptions on the wire; DB payloads are unchanged, and expired images are not backfilled. Text-only primaries remain image-free after automatic/overflow compaction rebuilds; overflow retries reapply inference overrides. Fallback activity uses the foreground run token and is separately registered for interrupt/shutdown cancellation. Non-cancelled description attempts persist `description_status` (`complete`/`failed`) so failures are not retried after every step or reopening; cancelled attempts stay retryable. User image ingestion enforces a 4 MiB decoded cap for paths and supplied base64, bounds image reads, and persists explicit oversize/unavailable markers. Malformed context rows log session/message/sequence plus a payload-free JSON diagnostic; result repair remains effective.

**Provider selection:** session creation prefers registered Anthropic, then OpenAI, then the first `available_ids()` entry. With none registered it publishes a clear error and returns an empty session id. The `chatgpt` provider type (Codex OAuth, labeled "ChatGPT (Experimental)" in Settings) registers only while signed in; unsigned-in entries stay visible in the toolbar dropdown greyed-out with "(sign in via Settings)" and can never be marked — `SelectProvider` refuses disabled items. It uses the unofficial Codex CLI backend, which may break or violate the ChatGPT terms of service. **ChatGPT usage hygiene** (`lib/src/provider/codex_params.cpp`, `build_codex_body`): `instructions` carry ONLY the stable system prompt; any `system_dynamic` is appended as the LAST `input` item (the engine itself sends per-step state as history status updates — see Append-only history) — the Responses prompt is tools → instructions → input, so dynamic text in `instructions` re-bills the whole history uncached on every todo change. `prompt_cache_key` is the session id (`LLMRequest::cache_key`, set by the engine's `apply_inference`). Reasoning models get `include:["reasoning.encrypted_content"]`; finished reasoning items arrive via `StreamCallbacks::on_reasoning_item`, are persisted on the assistant row as `reasoning_items` (`{model, item}`), and replayed as `openai_reasoning` blocks only when the provider's `replays_reasoning_items()` is true (engine sets `ContextBuilder::replay_reasoning_model`) and only for the producing model — never on Anthropic/OpenAI wires. `get_model_context` lazily loads the Codex models catalog on a cache miss (15 s timeout, 5-min backoff after failure) so a provider recreated by a Settings save doesn't fall back to the prefix table's (larger) window and silently disable auto-compaction. Image descriptions also request `reasoning_effort` `"low"`.

**Agentic loop** (`lib/src/engine/engine.cpp`): `SessionEngine` spawns one `std::thread` per session. The thread runs a **renewable per-turn step budget** (default `max_steps=50`, configurable via agent config or the per-session Inference override): each user turn starts with a full window, and a `todo_write` that raises the completed-item count above the turn's high-water mark (`completed_high_water`, seeded from the store at loop start so earlier turns' items can't be re-completed for a renewal) resets `steps_left` to the configured maximum — so a large multi-file change doesn't die mid-work while the model is still progressing. Two guards keep renewal loop-proof: only *new* completions renew (re-completing or flip-flopping a status never does), and a hard per-turn ceiling of `kStepCeilingMultiplier * max_steps` (4×) terminates even an agent that farms trivial todo completions forever. The loop tracks a monotonic `iter` alongside the renewable `steps_left`; `iter` (not the budget) feeds `last_compaction_step_` and `should_compact_with_hysteresis`, because a renewed counter that moved backwards would make the hysteresis difference negative and silently suppress auto-compaction. Budget exhaustion surfaces as one of two distinct `StepFailed` messages: "Turn step budget exhausted (N steps without completing a todo)" vs "Hard step ceiling reached (M steps this turn)". Loop body: `ContextBuilder::build()` → `Provider::stream()` → collect text/tool-calls via `StreamCallbacks` → execute tools via `ToolRegistry` → repeat if `FinishReason::ToolUse`. Tool definitions are filtered per session mode through the shared `tool_allowed_in_mode()` (`lib/include/haicode/tool.h`), and the same function is re-enforced at execution time in `ToolRegistry::execute_impl` against `ToolContext::mode` — a provider returning a call for a tool hidden from the wire request gets a failed (`[mode restriction]`) tool_result, not an execution. Failed tool results persist `error + "\n" + output` so bash diagnostics survive alongside the exit status. An `std::atomic<bool>` per session allows interruption between steps. If any tool returns `result.denied == true`, the loop publishes `StepFailed` and breaks immediately. `session_running_` (a `std::map<string,bool>` under mutex) tracks whether a session thread is active — do not use `std::thread::joinable()` for this, as it returns true even after the thread finishes. The step-budget text (`render_dynamic_prompt()`, never in the system prompt, where a per-step change would invalidate the cached history behind it) is emitted only in the final stretch of the turn — the last `max(1, min(10, max_steps/2))` steps of the current window; before that `render_dynamic_prompt()` returns an empty string. Within that window the wording escalates as the budget depletes: a "getting tight" line at 5–14 steps left and a "CRITICAL" line at 1–4 steps left, so the model reprioritizes toward completing a todo (which renews) before exhaustion. Provider/model changes are re-read from the session every step; a provider switch re-fetches the provider object and refreshes the interrupt cancel map (`session_providers_`). Transport failures and non-2xx responses surface through `on_error` → `StepFailed` — never an empty assistant turn. `interrupt()` also releases that session's pending `ask_user` wait with an "(interrupted)" answer. The build hook (after `write`/`edit`) runs through the shared cancellable runner (`util::run_subprocess`) in the session directory under a 300 s timeout with a 100 KB output cap — a backgrounded build child returns promptly instead of holding the hook for the timeout. Shutdown is per-session: `~SessionEngine()` flips `shutting_down_` (submit/continue/compact refuse to spawn), sets interrupt flags, snapshots providers/threads/flags under `mu_`, then joins with no locks held — concurrent sessions run in parallel and share the one SQLite connection (serialized build, asserted in tests).

**Transcript joins mid-turn** (`InFlightStream`, `load_with_in_flight`, `engine.h`): a step's assistant row is persisted only when its stream ends, so a frontend that loads a session mid-reply needs the unpersisted part too. Each step registers an `in_flight_` entry (step id = its `assistant_message_id`) BEFORE publishing `StepStarted`; every text/reasoning delta is appended to it under `in_flight_mu_` and then published (outside the lock) with its byte `offset`. All transcript rows are written through `append_transcript_row()`, which appends, bumps the session's `row_gen_`, and (for the assistant row) drops the in-flight entry in one critical section; `Prompted`, `ToolCalled` (the assistant row's gen), `ToolSuccess`/`ToolFailed`, and the `ask_user` answer rewrite (which also bumps the gen and sets `replaces_result`) carry that `row_gen`. `load_with_in_flight(sid, load)` runs the caller's store reads under the same lock and returns the in-flight snapshot + current `row_gen`, so every byte/row is either in what `load` read or in what follows — never both, never neither. Lock order: `in_flight_mu_` → store connection mutex; never under `mu_`; nothing is published while holding it.

**Append-only history** (prompt cache + thinking-block binding): `assemble_messages` renders every stored row to the same bytes on every request, whichever turn is current — step N's request is an exact prefix of step N+1's. Anything that rewrites an earlier row breaks the provider prompt cache from that row on and, on Claude models that bind thinking blocks to the conversation prefix (Opus 5.5, Fable 5.1, Sonnet 5.5), invalidates every later replayed thinking block (a 400 on accounts created on/after 2026-08-31). So: past-turn tool results are NOT truncated (compaction bounds growth; its serializer truncates when summarizing), one-shot skill bodies keep rendering after their turn, and per-step state rides the history as **status updates**: each step builds a `StepStatus` (final-stretch budget text, rendered todos — untracked in Plan mode — and the offline flag), `next_status_update(now, last_status_update(context_rows))` returns only the parts that CHANGED since the last update still in context (null when nothing changed; vanished parts get explicit lines: budget renewed, todo list empty, offline off), and the engine appends its labeled text to the request tail via `ContextBuilder::append_status_block` (onto the last user turn, else its own user turn) and persists the full update on the step's assistant row as `data["status"]`. `assemble_messages` replays each persisted update through the same helper just before its assistant turn, so the live tail and the replay are byte-identical on every provider's wire. The engine sends `LLMRequest::system_dynamic` empty; providers still honor it for other callers. The status decision is recomputed whenever the context reloads (compaction can drop earlier copies). Known remaining prefix rewrites: mode switches (tool list + mode block), skills/offline toggles (system/tool list), images aging out of the two-turn window, compaction.

**Auto-compaction** (`SessionEngine::compact_history`): at the top of each loop step, if `config_.auto_compact` is on and the current input tokens reach `usable_input_tokens(window, max_tokens, compaction_buffer, auto_compact_threshold)` (= `min(window * threshold, window - max(output, buffer))`, reserve clamped to half the window so small windows still trigger), the older portion of the conversation is summarized into a **checkpoint**. Compaction is **non-destructive**: a `compaction_checkpoint` row records the `through_seq` boundary and `session_message` rows are never deleted — full history stays durable for scrollback and audit. Compaction is disabled when the context window is unknown (`get_context_window == 0`) — set `"models": {"<model_id>": <tokens>}` in config to enable it for unrecognized models. The **manual** Compact button (and overflow recovery) still work with an unknown window: `compact_history` estimates `window = current context tokens + 20%` so the fit-check and chunked-merge paths have a bound to work against. Window resolution order: winning user entry → live provider discovery → hardcoded prefix table (the server's reported window outranks the table because a local instance may be configured smaller than the model's nominal size). The `CompactionStarted`/`CompactionProgress`/`CompactionEnded` events drive a "compacting context… N%" indicator in both frontends (`CompactionProgress` maps the summarizer's streamed output onto a percent of the summary cap, rescaled per pass for chunked two-pass merges, and is published only when the percent changes); on success `CompactionEnded` also carries the committed `summary`, which both frontends render as a collapsible `[context compacted]` transcript entry (live from the event, on reload re-derived from `list_complete_checkpoints()` at the exact `through_seq` crossing — never stored as a `session_message` row, so the model context is unaffected). It also carries `context_tokens`, a chars/4+overhead estimate of the post-compaction request (checkpoint block + retained tail) that immediately refreshes the frontends' context meter instead of it sitting stale until the next provider usage report; it is persisted via `update_last_input_tokens` (`tok_last_input`) so relaunches show it, and the next `StepEnded` overwrites it with exact usage.

The boundary comes from `split_history()` (`lib/src/compaction/compaction.cpp`): walk backward over complete turns / tool exchanges until the `compaction_recent_context` token budget (default 10240) is spent. Rows at or below the previous checkpoint's `through_seq` are skipped without spending budget (otherwise the next compaction lands on the floor and no-ops). When the whole history fits the budget but ≥2 exchanges exist, the oldest is still summarized. Exchanges are never split mid-way — an oversized one stays structurally intact and is only truncated during serialization. Both slices are serialized by `serialize_history()` (roles, tool names, args, outputs, errors; large outputs truncated with an explicit marker; attachments as name+type).

**Inline (cache-friendly) summarization first.** A standalone summarizer prompt shares no prefix with the conversation, so every prompt cache misses and the whole history is re-processed — minutes of silent prefill on a local server. So when the caller has the conversation's own next request, `compact_history(..., cached_request)` first sends THAT request (system prompt, tools, messages, inference settings untouched) with `build_inline_summary_instruction()` appended to the tail via `append_status_block`; the prompt cache covers everything but the instruction. The model summarizes the WHOLE visible conversation (earlier checkpoint block included), and the verbatim tail kept after the checkpoint is budgeted at half of `compaction_recent_context` — that tail is covered twice by design (the "cheaper" variant: no boundary marker in the conversation, which would itself break the cache). An invalid draft or tool-call-only reply gets one corrective retry (draft as an assistant turn + `build_inline_summary_correction()` — still a prefix extension); a transport error, or a retry that still fails `validate_summary`, falls back to the standalone path below. Callers: the auto-trigger passes the step's `req`; `compact_now` rebuilds the last step's request from the per-session `last_request_shape_` snapshot (`StepRequestShape`, recorded by the loop each step; used only when its model/provider match the session's current ones — otherwise, or before any step ran in this process, standalone); overflow recovery passes nothing (its request no longer fits). Both instructions start with `kInlineSummaryMarker`; `is_inline_summary_request()` recognizes the call (test fakes use it). Every agentic step's request is built by the shared `build_step_request(shape, messages, &status_update)` (`engine.h`) — messages → `ContextBuilder::build`, status update at the tail, inference overrides, cache key — so the loop and `compact_now` cannot drift.

**Standalone summarizer** (fallback, and the only path for overflow recovery): the summary uses a fixed Markdown template (`build_summary_prompt`) requiring sections Objective / Constraints & Decisions / Completed Work / Active Work / Blockers / Next Actions / Relevant Files, merging the previous summary + aged retained context into ONE summary (no segment archives). The request is fit-checked against the window (oversized inputs fall back to a bounded two-pass chunked merge), validated by `validate_summary` (heading match is case-insensitive and "&" ≡ "and") with one corrective retry, then committed atomically via `complete_checkpoint`. On failure/interrupt the checkpoint row is marked failed and the previous boundary stays active; a `pending` row left by a crash is ignored (`latest_complete_checkpoint` only reads complete rows). Summarizer `StreamCallbacks` must set `on_finish` — providers call it unconditionally and an empty `std::function` aborts.

Context assembly always goes through `load_context_messages()` → `apply_checkpoint()`: with a completed checkpoint, only records `seq > through_seq` are sent, preceded by one synthetic `compaction_summary` row carrying `render_checkpoint_block()` (labeled HISTORICAL CONVERSATION; deliberately does NOT re-embed `recent_context` — those rows are still live and re-embedding would double-count ~10k tokens). `assemble_messages` emits the block as an assistant turn, preserving user/assistant alternation; a stub user turn is inserted if the tail starts with an assistant turn.

**Overflow recovery**: a provider error matching provider-specific overflow markers (`context_length_exceeded`, `request_too_large`, `prompt is too long`, `input length and max_tokens exceed`, `maximum context length` — via `classify_provider_error` in `lib/src/util/provider_error.cpp`), when nothing has streamed yet, triggers one checkpoint compaction and a single retry through the same assembly path; a second overflow surfaces as `StepFailed`. Bare "context"/"exceeds" substrings deliberately do NOT match, so unrelated errors (e.g. "exceeds your quota") never trigger compaction.

**Transient retries**: transient errors (overload, timeout, connection, 5xx, 429/529/rate-limit — same classifier) are retried up to 3 times with exponential backoff (0.5s/2s/8s, cap 10s), still only while nothing has streamed; a server-sent `Retry-After` header (seconds form, captured by `HttpClient::post_sse` via `CURLOPT_HEADERFUNCTION` and appended to the error text as `[retry-after: N]`) extends the wait to `max(backoff, retry_after)`.

**Hysteresis**: `should_compact_with_hysteresis()` gates the trigger. After a successful compaction, a per-session `last_compaction_step_` (under `mu_`) is recorded; the next compaction is blocked for at least 2 steps even if tokens stay above threshold. This prevents runaway re-compaction in the degenerate case where the post-compaction tail is itself above threshold. `submit_prompt` resets the counter to `-1` so every fresh user turn re-arms the trigger. A `compaction_in_progress_` set enforces single-flight compaction per session (auto path and `compact_now` both check it).

`compact_now()` (used by the GUI's **Compact** button) claims foreground state under `mu_` and tracks its worker in `runner_threads_`. It registers its provider, stream token, and fresh interruption flag for cancellation, then uses the same prompt drain as the agentic runner. Prompts arriving during compaction run afterwards as distinct turns. Finished worker handles are moved under the lock and joined outside it.

**Session autonaming** (`config_.autoname_sessions`, default on): new sessions get a title without user action, in two stages. (1) In `store_prompt_row`, after appending the first `user_prompted` message, if the title is still empty `derive_heuristic_title()` produces a short title (first non-empty line, whitespace collapsed, ~60-char word-boundary truncation) and calls `SessionStore::update_title`. (2) At the end of `agentic_loop`, when the user-turn count (`user_prompted` messages) satisfies `count % 5 == 1` — i.e. turns 1, 6, 11, 16, … — and `autoname_llm_refine` is on, `refine_title_llm()` makes a one-shot `provider->stream()` call on a separately tracked maintenance worker (same model, `reasoning_effort` `"low"`, `max_tokens` 512 — reasoning counts toward the cap on reasoning models, so the old 48 could yield an empty title; only the first line is used — no tools). It never holds foreground running state or delays new prompts. Interrupted turns skip refinement; interrupt/shutdown cancel maintenance via its own scoped token, and shutdown joins it outside engine locks. `SessionStore::update_title_if_current` atomically compares the spawn-time baseline so stale work cannot overwrite a newer title. On the first call it generates a fresh ≤6-word title; on later calls it reconsiders — shown the current title and the full prompt history, the model either echoes the title verbatim (no write, no event) or returns a revised one. Both stages publish a `SessionRenamed` event, which the GUI relay forwards as `MSG_SESSION_RENAMED` (not gated on active session, so the sidebar refreshes regardless). The master toggle disables both; the refine flag disables only the LLM call.

**Providers** (`lib/src/provider/`): `AnthropicProvider` and `OpenAIProvider` each implement `stream()` (SSE) and `list_models()` (HTTP GET, reports HTTP status via an `error` out-param). `base_url` is the **complete API root** (scheme + host + path prefix + version segment); the code appends only the resource path (`/messages`, `/chat/completions`, `/models`), so the version must be part of `base_url`. Defaults: `https://api.anthropic.com/v1`, `https://api.openai.com/v1`. OpenAI's message format differs from Anthropic's; `translate_messages()` in `openai.cpp` converts between them, including converting Anthropic content arrays with `tool_use` blocks into OpenAI `tool_calls`. Register providers via `ProviderRegistry::register_provider()`. **Silent-stream limit:** `HttpClient::post_sse` aborts a transfer below 1 byte/s for `stall_timeout()` seconds (default 60 — hosted APIs send keep-alives). Self-hosted servers send nothing while they prefill the prompt, and an uncached large prompt (compaction's summarizer re-sends the whole older history with a different prefix, so no KV-cache reuse) prefills for minutes — so `OpenAIProvider` sets `openai_stall_timeout(flavor)` (`openai_params.h`): 30 min for vLLM/llama.cpp/LM Studio/Ollama. llama.cpp additionally gets `return_progress:true`, so prefill streams `prompt_progress` chunks (role-only delta, `content:null`; the parser skips them) instead of silence; builds that predate the field ignore it (newer builds also send SSE comment pings every 30 s by default). Interrupt cancels at any point regardless of the limit. `stream()`/`cancel()` take an optional per-run stream token; `interrupt()` cancels only that session's in-flight stream (two sessions can share one provider object), and an empty token — used by `~SessionEngine()` — sweeps every stream on the provider.

The app supports **any number** of providers. Each `ProviderConfig` in `AppConfig::providers` (a `map<id, ProviderConfig>`) has a `type` of `"anthropic"`, `"openai"`, or one of the flavored OpenAI-compatible servers: `"ollama"`, `"vllm"`, `"openrouter"`, `"lmstudio"`, `"llamacpp"`; when empty it is inferred from the id (`"anthropic"` → anthropic, anything else → openai). The GUI iterates the map to register providers. The factory functions `make_anthropic_provider()` / `make_openai_provider()` take an optional `id` so each instance reports a distinct id to the registry. Flavored providers are constructed via `make_openai_compat_provider(api_key, base_url, id, flavor)`, which applies a flavor-specific default `base_url` when one isn't supplied (e.g. `lmstudio` → `http://localhost:1234/v1`, `ollama` → `http://localhost:11434/v1`). Env-var fallback (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) applies only to providers whose ids are literally `"anthropic"` / `"openai"`; an OpenAI-compatible entry with no key but a `base_url` (e.g. local Ollama) registers keyless.

**Model database** (`lib/include/haicode/model_db.h`, `lib/src/util/model_db.cpp`; editor: Settings → Model Database…): every per-model lookup — context window (`"models"`), output cap (`"max_output"`), vision (`"vision"`), price (`"pricing"`) — treats the user's config entries (keyed by model id OR prefix) and the built-in table as ONE prefix database: keys match case-insensitively as prefixes, the longest matching key wins, and a user key wins a tie with a built-in key. So an exact-id entry always wins, re-keying a built-in prefix replaces that row, and a short user prefix (`"gpt"`) only covers ids no longer built-in key matches (it never shadows `gpt-5.5`). Pricing compares the matched MODEL part (override keys may carry a `provider_id:`/`kind:` prefix; built-ins a `kind:`/`*:` one), and a winning override is flat — it replaces any built-in tier ladder in `compute_step_cost`. Output caps are clamped inside the providers (`clamp_max_tokens`, no config access), so `HaiCodeApp::_SyncMergedConfig` installs the merged `"max_output"` map process-wide via `set_max_output_overrides`; the other three are a live engine snapshot (`SessionEngine::model_overrides()` / `set_model_overrides()`, swapped under `model_db_mu_`; `_SyncMergedConfig` pushes it) — engine and GUI read that snapshot, never `config().model_contexts/model_vision/pricing` (construction-time values). `ModelDatabaseWindow` (`gui/src/ModelDatabaseWindow.cpp`) lists `build_model_database()` rows (union of built-in keys and user keys, values RESOLVED for an id equal to the key, `*` = from a user entry, `+` = base of a built-in tier ladder) with search / only-mine filters and Add/Edit/Revert; it reads and writes the GLOBAL config itself through `save_model_db_entry` (atomic via `update_config_file`, empty entry = revert) and posts `MSG_MODEL_DB_CHANGED`, on which `HaiCodeApp` reloads `global_layer_`, re-merges (pushing overrides live — no engine recreation, running sessions are not interrupted), and MainWindow re-resolves its context meter.

**Context-window discovery** (`get_context_window()` in `lib/src/util/model_info.cpp`, declared in `model_info.h`): resolution order is (1) a user entry (`"models": {"<model_id or prefix>": <tokens>}`) that wins the prefix database (`user_context_window()`), (2) live discovery when a `Provider*` is passed: `provider->get_model_context(model_id)` — the path used by flavored local servers so the context meter and auto-compaction work without manual config, (3) the prefix database (longest-prefix match against the hardcoded table of common Anthropic/OpenAI/Llama models; a shorter user prefix applies only where no built-in key matches), (4) `0` (unknown). Each flavor discovers context differently (`ServerFlavor` enum in `lib/include/haicode/model_context_parse.h`):
- **vLLM / OpenRouter**: context carried inline in the OpenAI-compatible `/v1/models` `data[]` entries (`max_model_len` / `context_length` respectively); parsed during `list_models()` into a cache.
- **LM Studio**: the OpenAI-compatible `/v1/models` carries no context. `fetch_lmstudio_context()` calls the native `GET /api/v1/models` (the deprecated `/api/v0` is not used), whose `{"models":[{key, max_context_length, loaded_instances:[{config.context_length}]}]}` shape is parsed by `parse_lmstudio_native_models()`. The OpenAI `/v1/models` `id` matches the native `key` exactly. A matched model with a non-empty `loaded_instances` returns its runtime window (`config.context_length`); otherwise the model's native `max_context_length`. If no key matches, the first model with a loaded instance is used (LM Studio typically serves one active model behind the OpenAI endpoint). Lazily fetched on first `get_model_context()` call and cached.
- **Ollama**: `POST {native_root}/api/show` → `model_info["llama.context_length"]`; lazily fetched. Note this is the GGUF-declared native max, not the runtime `num_ctx` (default 4096) — may overstate the effective window.
- **llama.cpp**: `GET {server_root}/props` → `default_generation_settings.n_ctx`; lazily fetched.

All four pure parse functions (`parse_model_context_inline`, `parse_lmstudio_native_models`, `parse_ollama_show`, `parse_llamacpp_props`) are unit-tested in `lib/tests/test_model_context.cpp`.

In the GUI, the provider dropdown is built dynamically via `MainWindow::RebuildProviderMenu()`. Each menu item carries its real `provider_id` in its `BMessage`; the `MSG_FETCH_MODELS` handler reads it from the message (never from the label). `SelectProvider()` matches by exact id and stores it verbatim — it must not coerce to two values, or restored sessions using a custom id would be silently remapped. `SettingsWindow` presents an add/edit/remove list editor; on save it serializes the full providers map and `HaiCodeApp` re-runs the registration loop, recreates the engine, and calls `RebuildProviderMenu()`. Both the settings save and the providers update confirm through `_ConfirmDisruptiveChange()` first when any session is running (see "Disruptive changes confirm first" above).

**Pricing caveat:** built-in prices are keyed by provider KIND (`"anthropic:"`, `"openai:"`) or `"*:"`, and `lookup_pricing()` resolves through the provider's kind, so a custom-id Anthropic provider still prices. The per-model `pricing` config override (keyed `"<provider_id>:<model>"`, `"<kind>:<model>"`, or a bare model id/prefix — the Model Database editor writes bare keys) remains the escape hatch for proxies with their own rates.

**Pricing** (`lib/src/pricing/`): Handles model costs, token usage calculations, and pricing lookups for various providers. `TokenUsage` buckets are disjoint and each billed by `compute_cost`: `input` excludes cache reads/writes and `output` EXCLUDES `reasoning` — a provider whose API folds reasoning into its output count must subtract it (`parse_codex_usage`), or reasoning is billed twice.

**Cost accounting** (engine): every cost write goes through `SessionEngine::record_usage()` → `SessionStore::update_cost()` + a `CostUpdated` event carrying the persisted session totals — agentic steps and maintenance calls (title refinement, compaction summarizer, vision describer) alike, so the GUI status strip (`MSG_COST_UPDATED`; `_HandleStepEnded` no longer accumulates totals) never drifts from the store. Each step is priced with the model that ran it (model re-read every step), so mid-session model switches are costed correctly; there is a single running total, no per-model breakdown. While a request streams the engine tracks usage in flight: `StreamCallbacks::on_usage` (Anthropic: input/cache at `message_start`, output at `message_delta`) plus streamed text/reasoning/tool-input characters feed `estimate_inflight_usage()`, published throttled (2/s) as `CostProgress` → `MSG_COST_PROGRESS`, shown as `~$x` on top of the persisted total until the next `CostUpdated`. A stream that ends without `on_finish` is still priced from that estimate: an interrupted step when the provider reported input or output streamed, a failed step only when output streamed (errors before any output aren't billed). Only real usage reports move the context meter: `update_cost(..., sets_context)` is false for maintenance calls and estimates (keeps `tok_last_input`), and `StepEnded` omits `context_tokens` when no report arrived.

**Session** (`lib/src/session/`): Manages session-specific events and state.

**Permission gate** (`lib/src/permission/permission.cpp`): `PermissionGate::evaluate()` reports effect + reason + source + rule index without side effects; `check()` wraps it and resolves an `Ask` through the ask callback. Layer precedence, highest first: (1) exact temporary grants — literal (action, resource) equality, deliberately NOT globbed, so a resource containing `*` from a tool can't authorize more than displayed; (2) legacy pattern grants (`add_allow`, fnmatch); (3) session toggle rules (auto-write → `{"write","*",Allow}`, bypass → `{"*","*",Allow}`, reads-everywhere → `{"read","*",Allow}`); (4) configured rules (global file first, project file appended after). Within a layer the LAST matching rule wins; an `Ask` result falls through to the next layer (session layers can therefore override a configured Deny — preserved behavior), but the highest-precedence matched `Ask` is reported with that layer's source instead of the anonymous `"prompt"` no-match default — `ToolRegistry::evaluate()` relies on that distinction to let an explicit Ask rule override a built-in exemption. Resource matching is segment-aware for bash pattern Allows (Task 20): a bash rule whose resource contains glob metacharacters and whose effect is Allow only matches when `bash_pattern_authorizes()` says the pattern covers every `;`/`&&`/`||`/`|`/newline/`&`-separated segment of the command; Deny patterns and all non-bash actions keep whole-string fnmatch. Only an explicit `Allow` executes: `ToolRegistry::execute()` sets `result.denied = true` for both `Deny` and an unresolved `Ask` (no matching rule and no ask callback), so library consumers without a UI never get silent fall-through execution. `ToolRegistry::evaluate()` (const, no execution) is the same decision path factored out — the Permissions center's inspector uses it, so inspector and real execution can't diverge. Evaluation order inside it: mode and offline checks first, then the absolute system-root exemption, then the rule layers (`gate.evaluate`), and only when NO layer matched (anonymous `"prompt"` default) does a built-in exemption apply as fallback — so a configured or session Deny/Ask on `web_search`, `web_extract`, `screenshot`, read-only `process`, read-only `git`, or an in-project read takes effect (an `Ask` routes through the normal broker prompt); session-over-config precedence is unchanged because it lives inside `PermissionGate::evaluate`. `ToolRegistry::execute_impl` also enforces the session mode at execution time via `tool_allowed_in_mode()` (`ToolContext::mode`): a tool hidden from the wire request in Plan/Chat mode fails with a `[mode restriction]` error (`denied=false`, turn continues) instead of executing — Chat blocks even `read`, before the working-dir bypass. After an approval wait resolves, `execute_impl` re-checks `ctx.interrupt` so an interrupt that landed while the user was deciding stops the call (`[interrupted]`, `denied=true`) before it executes.

**Permission request broker** (`lib/src/permission/permission_requests.{h,cpp}`): `PermissionRequestBroker` owns approval wait state. Engine workers block in `submit()`; the GUI resolves by request id (`resolve()`), never via promise pointers. Exactly-once semantics: duplicate, stale, or post-cancellation replies are refused without side effects. `AllowForSession` installs the gate's exact grant BEFORE waking the waiter, so approval and grant can never be observed out of order. `cancel_session()` denies that session's pending waits and auto-denies further submissions until `allow_submissions()` re-arms at the next run start; `cancel_all()` is the shutdown path; `reopen()` lifts a cancel_all for engine recreation (settings/directory changes). Missing delivery callback fails closed (deny). `SessionEngine::set_permission_broker()` routes gate asks through the broker with full context (tool name, call id, working dir); `interrupt()` calls `cancel_session`, `shutdown()` calls `cancel_all` BEFORE joining workers (a parked worker can never hang destruction).

**Source-aware policy storage** (`lib/src/config/config.cpp`): `load_permission_document(path)` reads one file's `permissions` array un-merged, with a canonical fingerprint; `save_permission_document(path, rules, expected_fingerprint, err)` re-reads + validates the document, rejects conflicting edits since the fingerprint (cosmetic reformatting is NOT a conflict), replaces only the `permissions` array (preserving unrelated/unknown keys; empty list removes the key), writes through a temp sibling + atomic rename, and creates missing parent dirs. The Permissions center edits global and project sources independently; `MSG_PERM_POLICY_SAVED` makes `HaiCodeApp` reload config and call `set_rules()`.

**Config** (`lib/src/config/config.cpp`): Global config at `B_USER_SETTINGS_DIRECTORY/haicode/config.json`; project config at `<project_dir>/.haicode/config.json`. Loading is two-stage: `load_layer(path)` parses one file into a `ConfigLayer` (values + a `present` set recording exactly which keys/subkeys the file supplied — `ConfigLoader::load_file()` is a thin values-only wrapper), and the free `merge(base_layer, overlay_layer)` applies overlay keys only when *present*: absent project keys never clobber globals, explicit values equal to struct defaults still override (booleans can be re-enabled), and provider entries merge per subkey so a project `base_url` can't drop the global `api_key`. Collections (`permissions`, `instructions`, `skills`) append (skills dedup); per-key maps (`models`, `vision`, `pricing`, search `api_keys`) overlay per key. `auto_compact_reserve`, `MCPServerConfig`/`mcp`, and `ProviderConfig::env` were removed — they were parsed but never consumed. **Project configs are untrusted input** (Task 9): `load_with_layers()` routes the project layer through `load_project_layer()`, which NEVER merges project `providers` (credentials/endpoints are global-only) and strips the authority-granting keys (`permissions`, `build_command`, `agents`, `web_search.api_keys`) unless the global file's `"trusted_projects"` map holds a matching `project_gated_fingerprint()` for `realpath(project_dir)`; the pre-strip state comes back as `ProjectTrust` (needed/granted/fingerprint/summary) so the GUI can prompt (`HaiCodeApp::_MaybePromptProjectTrust`, fail-closed: "Don't Trust" is the default button). Any change to gated content changes the fingerprint and re-prompts; cosmetic reformatting does not. The global config also stores `last_directory` (the most recently used project directory). Notable project-only fields: `build_command` (shell command run after every successful `write`/`edit` — see Build hook below). `HaiCodeApp` keeps the GLOBAL layer (`global_layer_`, loaded via `load_layer(global_config_path())`) separate from the merged `config_` the engine/UI read: a Settings save applies fields to `global_layer_.values`, persists via `sync_global_scope()` (replaces exactly `global_scope_keys()`, preserves `permissions`/`last_directory`/unknown keys, drops a legacy global `build_command`), and writes the build command to `<project>/.haicode/config.json`; `_SyncMergedConfig()` then re-derives `config_ = load_with_layers(global_layer_, project_dir_)` and refreshes gate rules. **All config writes go through `update_config_file(path, mutate, err)`** — it reads the existing document, refuses to touch an unparseable file (a hand-edit typo must not cost the user their API keys), applies the mutation (preserving unrelated/unknown keys), and writes through `util::atomic_write_file` (mkstemp + fsync + rename) as 0600; the GUI wraps it in `save_config_at()` which surfaces failures in a `BAlert` instead of swallowing them. Never write a config file with a bare `std::ofstream`. `libhaicode` links `-lbe` because `config.cpp` uses `BPath` and `find_directory`; executables that link `libhaicode` get this transitively.

**Skills** (`lib/src/skills/skills.cpp`): User-authored markdown files whose content is injected into the system prompt when enabled. Discovery (`list_skills`) scans `<settings>/haicode/skills/*.md` (global) and `<project>/.haicode/skills/*.md` (project); a project file shadows a same-name global one. Skill id = filename (e.g. `git-commit.md`). Optional `---` frontmatter carries `name:`/`description:` (`name` is display-only; `description` is emitted into the prompt as a "When to use:" line — the rest of the frontmatter is stripped by `parse_skill_frontmatter`). `build_skills_block` opens with a directive preamble ("active operating instructions, not reference documentation: apply…") so the model treats skills as behavior to execute rather than reference material. Each section leads with a `Location:` line naming the skill file's absolute path and its skill directory, with an explicit instruction to resolve the skill's relative file/script references against the skill directory (not the project directory — tools resolve relatives against the project, so global/pack skills would otherwise point at the wrong tree). The block builder takes the session mode (`"build"`/`"plan"`/`"chat"`); in plan/chat it appends a capability note to the preamble stating which execution tools are unavailable (plan: `bash`/`write`/`edit`/`external_terminal`; chat: no local access at all) so the model applies skills within what it can actually do. Per-session enablement lives in the session's `model_json["skills"]` array (MainWindow Skills tab → `SessionStore::update_skills`); defaults for new sessions come from the top-level `"skills"` array in config.json (`AppConfig::default_skills`, seeded by `create_session`, editable in the Settings Skills tab). `agentic_loop` appends `build_skills_block()` to the stable system-prompt body after `agents_md_block` and re-reads the list and mode each step, rebuilding when either changed so mid-session toggles land on the next step. The block is capped at 64 KB total; a skill that alone exceeds the cap, or no longer fits the remaining budget, is omitted individually with an in-band `[skill '<id>' omitted: …]` marker — later smaller skills still land. `$HAICODE_SKILLS_DIR` overrides the global dir (legacy `$HPCODE_SKILLS_DIR` still accepted for one release; tests).

**Slash-command skill invocation** (one-shot): a message starting with `/<id>` (e.g. `/caveman write a commit`) invokes a skill for that single turn — no Skills-tab toggle needed, enabled or not. `parse_skill_invocation` matches the first token against `list_skills(project_dir)` in tiers (exact id → filename stem; non-matches like `/boot/...` paths pass through untouched). `submit_prompt` resolves the body at submit time via `build_skills_block({id}, mode_label(get_mode(...)))` — the one-shot block carries the same `Location:` line and mode capability note as the session block — and stores it on the `user_prompted` row's `data_json` (`skill`, `skill_args`, `skill_block`; `skill_active` instead when the skill is already session-enabled — no duplicate body). The row's `text` keeps the verbatim command so transcript replay is unchanged. `ContextBuilder::assemble_messages` emits the framed body + args (never the raw command) identically in every turn (append-only history) — the framing scopes the instructions to that one message ("they do not apply to later turns"). Works with `mode_notice` (notice first) and the attachment content-array path (skill text block before the user text).

**Tools** (`lib/src/tool/tools.cpp` + `lib/src/tool/web_tools.cpp`): Twenty built-in tools — see Tool Details below.

### `gui/` — BeAPI (Haiku native) frontend

- `HaiCodeApp` (BApplication) owns all haicode objects as `unique_ptr`. On startup, reads `last_directory` from settings JSON if no command-line arg was given.
- `MainWindow` (BWindow) handles all `MSG_*` messages in the BeAPI looper thread. Holds `engine_` as a pointer (`haicode::SessionEngine*`) not a reference, updated via `SetEngine()` when settings change.
- `GuiEventRelay` subscribes to `SessionEventBus` from engine threads and forwards events as `BMessage` via `BMessenger::SendMessage()` (thread-safe).
- Permission requests: unresolved gate Asks route through `PermissionRequestBroker` (owned by `HaiCodeApp`; engine wired via `set_permission_broker`). The broker's delivery callback posts `MSG_PERMISSION_REQ` (structured request + `request_id`) to `MainWindow`; `PermissionWindow` replies `MSG_PERMISSION_DECISION` (deny=0 / allow-once=1 / allow-for-session=2) to `be_app`, which calls `broker_->resolve()` — exactly-once, keyed by request id. `AllowForSession` installs a literal (non-glob) exact grant before the waiter wakes. `MainWindow` shows one review window per session; extras queue (`pending_perm_queue_`) and surface via `MSG_PERMISSION_WINDOW_CLOSED`. The review window shows session/tool/category, a plain-language summary, the selectable full target, tool-specific previews (command, write content, edit old/new, git args), outside-project and build-hook warnings, and the truncated raw input; Deny is the default button and Escape/close denies. All permission state is session-scoped: the gate keys toggle rules and grants by session id, so switching the selected session never changes the rules a background session runs under. `HaiCodeApp` owns toggle-flag state (`_SyncSessionFlags` on switch, `_PersistSessionFlags` on change) — the old toolbar checkboxes are gone; controls live in the Permissions center.
- **Permissions center** (`gui/src/PermissionsCenterWindow.cpp`, opened via Settings → Permissions…): three tabs. *Session*: session selector, mode/directory readout, plain-language toggles (auto-writes / reads-everywhere / bypass-with-confirmation; mode-inapplicable ones disabled with an explanation), pending approval queue (approve/deny), and the temporary-grant list with individual/all revocation (both exact and legacy pattern grants; revocation affects subsequent checks only). *Policies*: source-separated global/project rule lists (add/edit/remove/reorder via `PermissionRuleEditWindow`), atomic saves with fingerprint conflict detection (`MSG_PERM_POLICY_SAVED` reloads config + gate rules), and an operation inspector running the shared `ToolRegistry::evaluate()` (reports effect/source/reason without executing or prompting). *Activity*: bounded per-session log of authorization outcomes since launch (no raw payloads), fed by the broker's notify callback. ## Key constraints

- **Never block the BeAPI looper thread** — all network/engine calls go through `be_app` or a detached thread posting back via `BMessenger`.
- **`B_SIZE_UNLIMITED` is only valid as a maximum size**, not a minimum. Use `B_SIZE_UNSET` for unconstrained minimum dimensions.
- **BeAPI `BScrollView` constructor**: use the 6-arg layout-aware form (no `resizingMode` parameter) when building layout-managed views. The 7-arg old-style form breaks layout and grays out child views.
- **SQLite schema**: `session`, `session_message` (types: `user_prompted`, `assistant_text`, `tool_called`, `tool_result`), `session_todo`, `compaction_checkpoint`. WAL mode + FK constraints (`ON DELETE CASCADE`) enabled; `sqlite3_busy_timeout` is 5000 ms at open. Schema versioning is `PRAGMA user_version` (currently 2): migration 1 creates `kSchema` + adds `tok_last_input`; migration 2 drops the never-used `permission` table (policy lives in config files + the in-memory `PermissionGate`) — add new migrations as numbered `if (version < N)` steps in `Database::migrate()`, never edit old ones. Every statement goes through the `DbStmt` RAII wrapper (`db.h`): write paths call `expect_done()` and throw `DbError` on unexpected results — a persist is never reported as success until SQLite confirms it. Engine entry points that persist on the GUI looper thread (`submit_prompt`, `inject_message`, `retry_last_turn`, `set_mode`, `seed_todos`, `create_session`, `update_provider_model`, `update_inference`) catch `DbError` and publish `StepFailed` ("database error: …"); loop-thread persists surface through `runner_main`'s barrier the same way. **Concurrency:** all sessions share ONE sqlite connection, so `SessionStore` serializes every public method with a store-level mutex (`conn_mu_`) — a public method must never call another public method (self-deadlock). `append_message` allocates its seq inside a single `INSERT … SELECT COALESCE(MAX(seq),0)+1`, and `replace_todos` runs under an RAII `DbTxn` (checked BEGIN/COMMIT, ROLLBACK on any failure) held across the whole transaction, so concurrent writers can neither collide on `UNIQUE(session_id, seq)` nor get absorbed into another thread's open transaction.
- **Tool context messages**: assistant messages that include tool calls must be stored and reassembled with Anthropic `tool_use` content blocks (not plain text). Missing these causes orphaned `tool_result` blocks in the next request, making the model repeat work it already completed.
- **Built-in exemptions are fallbacks below explicit rules** (`ToolRegistry::evaluate()` in `lib/src/permission/permission.cpp`): Haiku's system header/doc roots are absolute (no rule can deny them), but every other built-in allow applies only when NO rule layer matched: `read`, `ls`, `grep`, `diff`, `find`, `symbols` inside `ctx.working_dir`, `glob` when its literal prefix before the first wildcard (relative patterns joined with `working_dir` first) resolves inside the project, read-only `git` invocations, `web_search`/`web_extract`, `propose_plan`/`todo_write`/`ask_user`, `screenshot`, and `process list`/`check_port`. A configured or session Deny/Ask rule on any of these takes effect (an `Ask` routes through the normal broker prompt). Containment is symlink-aware (`path_resolves_within`: realpath on both sides, lexical fallback when either side fails to resolve), so an in-project symlink pointing outside the tree stays gated; `read` additionally opens with `O_NOFOLLOW` and re-checks the resolved target on `ELOOP` via the shared `path_is_always_readable` (`/boot/system/develop/headers`, `/boot/system/non-packaged/develop/headers`, `/boot/system/documentation` — the BeBook, userguide, man pages, and package docs; hardcoded in `is_within_always_readable_root()`, so config/session rules cannot override them); `glob` and `grep` report the `read` permission action (not their tool name), so a rule scoping them must use `{"action":"read", ...}`; read-only `git` is classified by `git_invocation_is_readonly(sub, args, working_dir)` (subcommand AND args, fail-closed): the fifteen query subcommands (`status`, `diff`, `log`, `show`, `blame`, `ls-files`, `shortlog`, `describe`, `rev-parse`, `merge-base`, `rev-list`, `ls-tree`, `cat-file`, `grep`, `for-each-ref`) unless an arg names an unsafe long option — `--output`, `--ext-diff`, `--textconv`, `--filters`, `--no-index`, `--contents`, `--ignore-revs-file`, `--open-files-in-pager`, `--file` — exactly OR as an abbreviation (parse-options subcommands expand unambiguous prefixes: `blame --content=` is `--contents`, `cat-file --text` is `--textconv`; a subcommand's own exact option that prefixes one — `--text` outside cat-file, blame `--ignore-rev`, rev-list `--filter` — stays allowed), or an unsafe short cluster (`grep -O`/`-f`, `blame -S`; a `grep -e` / `blame -L` value is skipped), or a `diff` path resolves outside `working_dir` (git silently switches to `--no-index` and prints any readable file; lexical check when `working_dir` is empty); `range-diff` is never read-only (its internal `log -p` runs textconv drivers no flag reaches); `branch`/`tag` only in listing forms (explicit `--list`, or `-l` for tag, unlocks trailing patterns); `stash` only via `list`/`show`; everything else, including `branch -D` and bare `stash` (which pushes), goes through the gate (residual limitation: rules match the bare subcommand, so an Allow rule for `branch` covers `-D` too). **When adding a new read-only tool that should bypass the gate inside the project directory when no rule says otherwise, add it to the exemption blocks in `lib/src/permission/permission.cpp` (search `name == "read"` to find them) and update this list.**
- **SSE parser state must persist across `write_cb` invocations within a request** (`lib/src/util/util.cpp`). `buffer`, `event_type` and `event_data` live on the request-local `RequestState` (a `post_sse()` stack object handed to libcurl as `CURLOPT_WRITEDATA`), not in function locals — libcurl invokes the write callback once per network chunk and a single SSE event (event:/data:/blank line) frequently straddles those chunks for large tool inputs (e.g. `propose_plan` markdown). Function locals silently dropped half-parsed events, truncating tool input JSON and causing `parse_failed` drops in the engine. Do not move this state back onto `HttpClient::State` — it is per-request, not per-client: two sessions can stream through one shared provider client concurrently, and per-client state crossed streams (A's tokens landed in B's callback), clobbered cancels, and raced on `buffer`. `HttpClient::State` now only tracks in-flight requests so `cancel()` can fan out.
- **`ToolResult` struct field order**: `{bool success, string output, string error, bool denied}`. The `denied` field is last — do not insert fields before it or existing brace-initializers break.
- Tool output is truncated to 100 KB (`MAX_OUTPUT` in `tools.cpp`).
- Session IDs are descending-timestamp sortable (newest first in `store_.list()`). Display human-readable dates by parsing `INT64_MAX - desc_hex` from the ID.

## Tool Details (`lib/src/tool/tools.cpp`, `lib/src/tool/web_tools.cpp`)

All tools share a `MAX_OUTPUT = 100 KB` cap and a `sq()` helper for safe single-quoted shell arguments. Web tools (`web_search`, `web_extract`) live in `web_tools.cpp` and are pulled into `register_builtin_tools()` via `register_web_tools()`.

**Shared subprocess runner** (`util::run_subprocess`, `lib/src/util/subprocess.cpp`): every tool that shells out (bash, grep, diff, git, find, process, screenshot) and the engine build hook run through one cancellable runner. Per command it forks a child in its **own process group**, gives it `/dev/null` stdin, merges stdout+stderr into one pipe, `chdir`s to the working dir, applies `extra_env`, and **closes every fd >= 3** so parent SQLite/socket handles never leak. The parent polls (100 ms): `*interrupt` kills the whole group (`interrupted`), the deadline does the same (`timed_out`), output is appended up to a 100 KB cap and **discarded past it** (`truncated` — the child is never SIGPIPEd, so a truncated success keeps its real exit code). Once the direct child exits, a bounded ~500 ms grace drain captures a backgrounded descendant's (`server &`) last output before returning — backgrounded commands return promptly and stay alive by design.

### BashTool (`bash`)
- Runs `{ command; }` via `util::run_subprocess` with `ctx.working_dir` as cwd (the runner chdirs — no `cd` wrapper)
- Timeout = model-supplied seconds, default 30, clamped to [1, 600]; `timed_out` → failed result "Command timed out after Ns"; `interrupted` → "Command interrupted"; no more exit-code-124 convention
- Exit code 0 → success; nonzero → failure with "Exit code: N" and output preserved
- Over-cap output appends `\n[output truncated]` without flipping success
- **Rule semantics (Task 20)**: a bash Allow pattern carrying glob metacharacters (`*?[`) must cover EVERY command of the invocation — the resource is split quote-aware at `;`, `&&`/`||`, `|`, newlines, and whitespace-delimited `&`, and each segment must fnmatch the pattern (`bash_pattern_authorizes()` in `lib/src/permission/permission.cpp`), so `make*` allows `make -j4` but not `make; rm -rf ~`; a segment containing command substitution (`$(…)`, backticks) never matches any pattern except the universal `*` (its output is unknowable at match time). Deny patterns keep whole-string fnmatch (over-matching a Deny is the safe direction); literal resources stay exact-equality; the session bypass `{"*","*",Allow}` matches every segment and still covers compounds. Redirect operators (`2>&1`, `&>`) and quoted separators are not command separators

### ReadTool (`read`)
- Resolves relative paths against `ctx.working_dir` (trailing slashes stripped before join)
- Rejects empty path; detects binary files (null byte scan of first 8 KB) and refuses them
- `offset` is 1-based (offset=1 starts at line 1, the default)
- Enforces 100 KB cap mid-read
- Error messages include `strerror(errno)`
- **`f.clear()` is called before `seekg(0)` after the binary scan** — `read()` past EOF sets `eofbit`; without the clear, `getline()` fails immediately and returns empty output for any file smaller than 8 KB

### WriteTool (`write`)
- Resolves relative paths against `ctx.working_dir`
- Creates missing parent directories by walking path components with `mkdir()`
- Rejects a missing or non-string `content` **before touching the file** (a missing key must not default to `""` — that would empty the target); an explicitly empty string stays legal
- Atomic write via `util::atomic_write_file()`: `mkstemp` on `<resolved-path>.tmp_write_XXXXXX` (O_CREAT|O_EXCL — can never clobber a pre-existing sibling), `fchmod` (to the target's previous mode when it existed — an 0755 script keeps its execute bits; 0644 for new files; an EXPLICIT mode argument always wins over both, so secret files (`config.json`, `openai-auth.json`) are written 0600 even over pre-existing loose bits), write loop + `fsync`, then `rename()`; temp unlinked on any failure. Haiku-specific: BFS attributes (`BEOS:TYPE` MIME, Tracker metadata) are copied from the old file onto the replacement before the fsync (a bare rename drops them — best-effort, individual failures skipped); a symlink `path` is resolved with `realpath()` and the write lands in the target, keeping the link; an unresolvable (dangling/loop) symlink is refused with an error and nothing is written. `util::ensure_owner_only(path)` tightens an existing file to 0600 when it carries group/world bits (startup hardening for secret files older releases created 0644); it is a no-op on already-tight and missing files

### GlobTool (`glob`)
- Absolute patterns (starting with `/`) bypass base directory prepend
- Permission action is `"read"` (not `"glob"`) so the "Allow reads outside trusted roots" session toggle covers it outside the project tree; a config rule scoping it must use `{"action":"read", ...}`
- `GLOB_MARK` removed — was adding unwanted trailing slashes to directory matches
- `globfree()` called unconditionally after `glob()` (always safe per POSIX)
- Returns error on `rc != 0 && rc != GLOB_NOMATCH`; GLOB_NOMATCH returns "(no matches)"
- Note: `**` recursive matching is not supported by POSIX `glob()`

### GrepTool (`grep`)
- Pattern, path, and include are all passed through `sq()` — no shell injection possible
- Permission action is `"read"` (not `"grep"`) so the "Allow reads outside trusted roots" session toggle covers it outside the project tree; a config rule scoping it must use `{"action":"read", ...}`
- Uses `/bin/grep` absolute path
- Relative search path resolved against `ctx.working_dir`
- Exit codes: 0 = matches found, 1 = no matches (success), 2 = grep error (returns failure)
- Runs via the shared runner (60 s timeout, interruptible); output capped at 100 KB with a `[output truncated]` marker
- Schema key is `"line_numbers"` (boolean, default true), not `"-n"`

### EditTool (`edit`)
- Reads the whole file into memory, refuses binary files (null byte scan)
- Counts `old_string` occurrences; requires `replace_all=true` if it appears more than once
- Empty `old_string` is rejected with a hint to use both fields for deletion
- Rejects a missing or non-string `new_string` before touching the file (a missing key must not default to `""` — that would delete `old_string`); an explicitly empty string stays legal (deletion by design)
- Replacement is in-memory (single-pass for `replace_all`, single `find` otherwise)
- Writes via `util::atomic_write_file()` — same mkstemp/mode-preserving path as WriteTool
- Required permission: `write`

### LsTool (`ls`)
- Resolves relative `path` against `ctx.working_dir`; defaults to the project dir if omitted
- Uses `opendir()`/`readdir()`; skips `.` and `..`
- Adds suffixes via `stat()`: `/` for directories, `@` for symlinks
- Output sorted with `std::sort` and capped at 100 KB
- Required permission: `read`

### ExternalTerminalTool (`external_terminal`)
- Double-forks: first child calls `setsid()` and detaches stdio, grandchild `execl`s `/boot/system/apps/Terminal`
- Invokes Terminal as `Terminal -w <working_dir> /bin/sh -c '<command>'` — the window closes when the command exits
- Returns immediately; output is **not** captured (designed for interactive TUIs like vim, REPLs)
- Distinct permission action (`external_terminal`) so prompts make clear which tool is asking
- Required permission: `external_terminal`

### ProposePlanTool (`propose_plan`)
- Available in both Plan and Build mode — no engine-level filter removes it
- Always allowed — `ToolRegistry::execute()` bypasses the permission gate (same as web tools)
- Writes the plan markdown to `<project_dir>/.haicode/plans/plan_YYYYMMDD_HHMMSS_<4-hex-rand>.md`
- Parent directory created with `mkdir()` walking (same pattern as WriteTool)
- Returns the on-disk path so the engine can surface it via `PlanProposed` and end the turn

### TodoWriteTool (`todo_write`)
- Always allowed — `ToolRegistry::execute()` bypasses the permission gate (same as `propose_plan` and web tools)
- Whole-list replace: the model sends the full todo list every call, never a delta; an empty array clears everything
- Each item requires `content` (imperative form), `activeForm` (present-continuous for the spinner), and `status` (`pending`, `in_progress`, or `completed`)
- The engine detects this tool by name, writes the parsed todos to the `session_todo` table, and publishes a `TodoUpdated` event; the tool itself only validates and echoes the input
- Available in both Plan and Build mode

### AskUserTool (`ask_user`)
- Always allowed — `ToolRegistry::execute()` bypasses the permission gate (same as `propose_plan`, `todo_write`, and web tools)
- Asks the user a disambiguation question with 2–5 preset options plus a free-form "Other" entry; the model passes `question` (string) and `options` (string array of 2–5 items)
- The tool itself only validates and echoes the request as a JSON placeholder (`status: "asking"`); the real answer arrives later — the engine detects `ask_user` by name, publishes `AskUserRequested`, ends the turn, and blocks the agentic loop on `asking_cv_` until `reply_to_ask()` is called
- Once the user replies (selects a preset or types custom text, or cancels), `SessionStore::update_tool_result_by_call_id(session_id, call_id, …)` overwrites the placeholder `tool_result` row's `output` with `{"answer": "..."}` — scoped to the session and the newest matching row, and pending asks are keyed by (session, call id), because OpenAI-compatible servers' call ids are passed through and some reuse them and the engine republishes `ToolSuccess` so the UI swaps the placeholder bubble for the picked answer; then the loop resumes with the real answer visible to the model as the tool result
- Available in both Plan and Build mode — the engine adds it to the Plan-mode allowlist so it survives the read-only tool filter

### DiffTool (`diff`)
- Writes proposed content to a securely-created scratch file in the **system temp directory** (`find_directory(B_SYSTEM_TEMP_DIRECTORY)` with a `/tmp` fallback, `mkstemp` on `haicode_diff_XXXXXX`) — never beside the target, so a preview against a read-only location (e.g. the packagefs-mounted system headers in Plan mode) succeeds; runs `diff -u <original> <tmp>` via the shared runner (30 s, interruptible), then `unlink`s it — a pre-existing sibling like `foo.tmp_diff` is never read or deleted
- Exit code 1 (differences found) is treated as success; exit code 2 is a diff error (returns failure)
- Returns `"(no differences)"` when the content is identical
- Always allowed within the project directory and the Haiku system header roots; paths outside go through the gate (`read` permission)

### GitTool (`git`)
- Runs `git -C <working_dir> <subcommand> [args...]` via the shared runner (300 s timeout, `ctx.interrupt` honored, `GIT_TERMINAL_PROMPT=0` in the child env so a credential prompt fails fast instead of hanging)
- **Read-only hardening (Task 20)**: when `git_invocation_is_readonly()` classifies the invocation, the command becomes `git -c core.fsmonitor= -c core.hooksPath=/dev/null -c gpg.program=false -c gpg.ssh.program=false -c gpg.x509.program=false -c log.showSignature=false -C … <sub> [--no-ext-diff --no-textconv]` with `GIT_OPTIONAL_LOCKS=0` in the env — the bypass path (and everything Plan mode may run) must not honor repo-local config that can execute programs (a repo setting `diff.external` to a script gets real diff text, never a driver run; a repo setting `gpg.program` + `log.showSignature` would otherwise run it on a plain `git log`) and `git status` must not rewrite the index. `--no-ext-diff --no-textconv` are appended for `diff`/`log`/`show` and after the verb of `stash list`/`show` (`stash list -p` runs textconv); `blame` gets `--no-textconv` (blame runs textconv by default). The classifier refuses the re-enabling `--ext-diff`/`--textconv`, so model args appended after the flags can't override them. Residual limitation: in-tree `.gitattributes` filter drivers (`filter.<name>.clean`) configured in the repo's own `.git/config` can still run on `status`/`diff` — the driver name is repo-chosen, so no fixed `-c` blanks it
- Subcommand allowlist (validated before execution): `status`, `diff`, `log`, `show`, `branch`, `blame`, `stash`, `add`, `commit`, `checkout`, `reset`, `remote`, `merge`, `rebase`, `pull`, `push`, `fetch`, `tag`, `shortlog`, `describe`, `rev-parse`, `ls-files`, `merge-base`, `rev-list`, `ls-tree`, `cat-file`, `grep`, `range-diff`, `for-each-ref`
- The tool description carries review guidance (bound `log` with `-n`; base via `merge-base`, `log --oneline <base>..HEAD`, `diff --stat <base>...HEAD`, then per-file `diff <base>...HEAD -- <path>`, because output over 100 KB is truncated)
- **Plan mode**: `git` is in the Plan allowlist but `ToolRegistry::evaluate` refuses any invocation the classifier does not accept with a `[mode restriction]` failed result (`denied=false`), checked right after the mode/offline checks and BEFORE every rule layer — no Allow rule, session bypass, or grant can make Plan mode commit, branch, or run a driver
- All args passed through `sq()` — no shell injection possible
- Non-zero exit with non-empty output returns `success=false` with the output in `error`
- Read-only invocations are allowed by default (built-in exemption when no rule matched), classified by `git_invocation_is_readonly()` (see the Permission gate notes: listing-only forms for `branch`/`stash`/`tag`, unsafe-option and outside-path guards, fail-closed); everything else goes through the gate (`git` permission, resource = subcommand name — granularity limitation: an Allow rule on a subcommand covers its mutating forms too)

### FindTool (`find`)
- Wraps `find(1)` with optional `-maxdepth`, `-type`, `-name`, `-mtime`, `-size` flags; runs via the shared runner (60 s, interruptible)
- All user-supplied values passed through `sq()` — safe against injection
- `type` is validated to one of `f`, `d`, `l` before being passed to the shell
- Relative `path` resolved against `ctx.working_dir`; defaults to `ctx.working_dir` if omitted
- Always allowed within the project directory and the Haiku system header roots; paths outside go through the gate (`read` permission)
- Fills the gap left by GlobTool, which does not support `**` recursive matching

### SymbolsTool (`symbols`)
- Heuristic C/C++ symbol search: finds definitions and classifies references, faster than grep for tracing fields and functions across files
- Three queries: `definition` (where a name is defined), `references` (every occurrence, classified), `callers` (usage sites only — `call` + `member_access`)
- **Tokenizer (`strip_non_code`)**: a state machine blanks out line/block comments, string literals, and char literals before matching, eliminating grep's false positives on identifiers mentioned in comments or strings; comment/string state persists across lines
- **Scope tracking**: a brace-depth counter plus a stack of enclosing class/struct names lets each hit be classified (`definition` / `call` / `member_access` / `declaration` / `mention`) and annotated with `(in ClassName::method)` for usage sites
- No `clangd` / `libclang` / index — pure `<regex>` over CODE-only substrings; unresolvable queries (templates, macros) degrade to candidate sets. C/C++ only at launch
- Always allowed within the project directory and the Haiku system header roots (read-only, `resource()` returns a resolved path like `find`); paths outside go through the gate (`read` permission)
- Cap: 200 hits with a `[truncated]` marker; output sorted by file then line, with a trailing `N hits in M files` summary

### ProcessTool (`process`)
- Three actions selected via the `action` field: `list`, `kill`, `check_port`
- **list**: runs `ps` via the shared runner (30 s, interruptible) and optionally filters output lines by a `filter` substring (header always stripped from the no-match path); returns `"(no matching processes)"` if filter matches nothing
- **kill**: calls `kill(2)` directly (not a shell command) with the given `pid` and `signal` (TERM, KILL, HUP, INT, USR1, USR2, STOP, CONT; default TERM)
- **check_port**: runs `netstat -n` via the shared runner (30 s, interruptible) and filters for lines containing `:<port>`; returns `"Nothing listening on port N"` if none found
- `list` and `check_port` are allowed by default (built-in exemption when no rule matched); `kill` goes through the gate (`process` permission, resource `pid:<N>`)

### WebSearchTool (`web_search`) — `web_tools.cpp`
- Backends: `ddg_lite` (default, no API key), `ddg_html` (HTML scraping), `exa` and `zai` (JSON APIs via `HttpClient::post_json`). Configurable via `AppConfig::web_search_engine`
- Exa/Z.ai need an API key: resolved from `AppConfig::web_search_api_keys[engine]` (config `web_search.api_keys.exa`/`.zai`), falling back to `$EXA_API_KEY` / `$ZAI_API_KEY`. Missing key → tool error before any network call
- Exa: `POST api.exa.ai/search` with `x-api-key` header; first `highlights` entry becomes the snippet. Z.ai: `POST api.z.ai/api/paas/v4/web_search` with `Bearer` auth; `content` truncated to 400 chars for the snippet
- Returns ranked results: title, URL, snippet — read snippets before calling `web_extract`
- `max_results` defaults to 5, capped at 10 (all engines)
- HTML parsing is in-process (no external deps); DDG may surface CAPTCHA errors
- Required permission: `web_search`

### WebExtractTool (`web_extract`) — `web_tools.cpp`
- Fetches one URL via `HttpClient` (libcurl) with a browser User-Agent
- Returns cleaned main-body text — nav, ads, scripts stripped (HTML stripper is ~400 lines, untested)
- `max_chars` defaults to 8000 and is clamped to `[1, 100 KB]` (the shared output budget — the model-supplied bound is untrusted); rejects non-http(s) URLs
- The output's `truncated` flag is `text_truncated || download_truncated`: a body over `HttpClient`'s 10 MB download cap aborts at the cap with the real HTTP code and surfaces `truncated: true` on an otherwise successful result
- Allowed by default (built-in exemption); can be gated with an Ask/Deny rule in the Policies tab (effective since the Task 18 rule-precedence change)
- Required permission: `web_extract`

### ScreenshotTool (`screenshot`) — `tools.cpp`
- Runs the system CLI `screenshot --silent --format=png [--window] [--delay=N] '<path>'` (`sq()`-quoted path) via the shared runner (15 s, interruptible); the CLI writes a PNG into the temp directory (`find_directory(B_SYSTEM_TEMP_DIRECTORY)` → `/tmp`)
- **Exit status is not trusted** — the CLI returns nonzero codes even on success; the tool validates the output file instead (exists, ≥24 bytes, PNG signature)
- Parses WxH from the PNG IHDR header (bytes 16–23, big-endian; no image library); enforces the same 4 MB cap as GUI image attachments (over-cap → error suggesting `window=true`)
- Returns a JSON object with a reserved `attachments` array (`{media_type, path, data_b64}`, same shape as user attachments); the engine strips it at the `tool_result` append site and persists it on the row, and `assemble_messages` emits it as Anthropic image blocks inside the tool_result content (OpenAI's `translate_messages` splits the blocks into a follow-up `image_url` user message)
- **Vision-gated**: hidden from the tool list unless `model_supports_vision()` says the active model accepts images (config `"vision"` entries + `kVisionModels` prefix table as one prefix database → fail-closed false). Re-evaluated per step, so a mid-loop model switch flips availability on the next step
- Allowed by default (read-only, shared screen state — a built-in exemption, so an Ask/Deny rule can gate it); available in Plan and Build modes, absent from Chat
- **Visible in the transcript**: tool bubbles collapse, so a successful capture also appends a non-collapsible system line ("Screenshot captured — image sent to the provider.") both live (`MainWindow::_HandleToolResult`) and on session replay (`_RebuildChat` matches the `tool_result` row's `call_id` back to the `tool_calls` entry from its `assistant_text` row)
- Config: `"vision": {"<model_id or prefix>": true|false}` joins the prefix table (longest key wins, user wins ties; also editable in Settings → Model Database…); editable in Settings → General as the "Vision:" dropdown (Auto/Yes/No, scoped to the selected default model — Auto removes the override, Yes/No write the `"vision"` key in config.json)
- **Vision fallback**: `"vision_fallback": {"provider": "...", "model": "..."}` names a vision-capable (provider, model) pair (editable in Settings → General dropdowns). When the session's primary model is text-only and the fallback is configured: at `agentic_loop` start, a backfill pass (`SessionEngine::backfill_attachment_descriptions`) one-shot describes every persisted attachment (user_prompted and tool_result rows) lacking a `"description"` key via `SessionEngine::describe_image` (same synchronous provider-stream pattern as `refine_title_llm`), persists descriptions through `SessionStore::update_message_data` (describe-once; clamped to 4 KiB; survives restart), and `ContextBuilder::assemble_messages(..., model_accepts_images=false)` emits `[image: path — described by vision fallback: ...]` text blocks instead of image blocks. The screenshot-tool vision gate is relaxed (`!vision && !vision_fallback_ready()`), so the tool stays available with a fallback; switch to a vision model sends the original image bytes as-is. Fallback readiness gate: model non-empty and its provider registered — the fallback is an explicit user choice, trusted without a `model_supports_vision` prefix-table check (local vision servers aren't in the table). Fallback describer, title-refinement, and compaction-summarizer usage IS added to session cost accounting (Task 26): each maintenance call captures `TokenUsage` from its `on_finish` and calls `store_.update_cost` through the same `compute_step_cost` resolution as foreground steps

## Build hook

Set `build_command` in `<project_dir>/.haicode/config.json` to automatically run a build after every successful `write` or `edit` tool call:

```json
{ "build_command": "make -C build -j4 2>&1" }
```

If the command exits non-zero, its output is appended to the tool result with a `[build_hook]` prefix and `result.success` is set to `false`, so the model sees compile errors immediately and can fix them in the same turn rather than discovering them steps later.

After every run (success or failure) the engine publishes a `BuildHookResult` event (`lib/include/haicode/events.h`). Both frontends display a brief system line — `build ✓` or `build ✗ (exit N)` — so the user can see at a glance whether the hook ran and passed, even when it succeeded silently.

The hook runs synchronously in the engine thread. Avoid commands that take more than ~30 seconds, as the engine is blocked for the duration. The agent detects the build system and sets this field automatically when starting work on a new project (CMake → `make -C build 2>&1`, plain Makefile → `make 2>&1`, npm → `npm run build 2>&1`, Cargo → `cargo build 2>&1`).

## Plan mode

When a session is in Plan mode, the engine:
- Filters `bash`, `write`, `edit`, `external_terminal` out of the tool list — the model literally cannot attempt them
- Keeps `ask_user` in the tool list (alongside `read`, `glob`, `grep`, `ls`, `find`, `symbols`, `git`, `diff`, `todo_write`, `web_search`, `web_extract`, `propose_plan`, `discard_plan`, `screenshot`) so the model can resolve genuine ambiguities with the user before proposing
- Restricts `git` to read-only invocations (`git_invocation_is_readonly()`, enforced in `ToolRegistry::evaluate` before any rule layer) so reviews can read history, diffs, and blame without Plan mode ever mutating the repository
- Injects `kPlanModeInstructions` (`lib/include/haicode/default_prompt.h`) into the system prompt
- Ends the turn automatically after a successful `propose_plan` call and publishes `PlanProposed` so the UI can show the review window

Plan mode instructions tell the model that reviews, analyses, and explanations are answered directly in its reply — `propose_plan` is only for implementation strategies — and give a git review workflow (base via `merge-base`, commit list, `diff --stat`, then per-file diffs). They tell the model to call `ask_user` with 2–5 concrete options if the request is ambiguous before researching or proposing. Questions that can be answered by reading the codebase should not be asked, and no more than one `ask_user` call should precede a proposal.

`_HandlePlanDecision()` in `gui/src/MainWindow.cpp`: on approval, reads the plan file stored in `pending_plan_path_` (set when `PlanProposed` fired), calls `haicode::parse_plan_tasks()` to extract the `## Tasks` checklist, and calls `engine_->seed_todos(sid, todos)` to write the list to the DB and publish `TodoUpdated` — so the todo panel is populated immediately before the engine resumes. Then calls `engine_->set_mode(sid, Build)`, `engine_->inject_message(sid, kPlanApprovedMessage)`, and `engine_->continue_session(sid)` unconditionally. The `inject_message` call appends a `user_prompted` message (the shared `kPlanApprovedMessage` constant from `lib/include/haicode/default_prompt.h`) so the model, on resume, knows the plan was approved and it is now in Build mode — without it, `continue_session` re-enters the loop with no new input and the model has to infer the state change from the tool list shifting. The UI refresh is gated on `sid == active_session_id_` but the session always resumes. On denial, the session stays in Plan mode; a "Plan discarded" system message is appended to the active chat but no mode change or `continue_session` is called.

**Plan task format**: `propose_plan` should include a `## Tasks` section with a markdown checklist for seeding to work:

```markdown
## Tasks
- [ ] Add BuildHookResult event to events.h
- [ ] Publish event in engine.cpp
- [ ] Handle event in GUI relay
```

`parse_plan_tasks()` (`lib/src/engine/engine.cpp`) reads lines from the `## Tasks` section until the next `##` heading or EOF. It accepts `- [ ]`, `- [x]`, `- [X]`, and plain `- ` prefixes. `activeForm` is derived by converting the leading verb to gerund (e.g. "Add" → "Adding") via a lookup table; unknown verbs fall back to the content string unchanged.

`engine_->seed_todos()` (`lib/include/haicode/engine.h`) calls `store_.replace_todos()` then publishes `TodoUpdated` — it is also callable from the GUI plan approval path and anywhere else a todo list needs to be set programmatically.
